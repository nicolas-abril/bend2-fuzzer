## F32.show: exact ties round to even in C and up in JS (2 findings)

`10640754062594961310`, `2687685315483489791`: both feed `F32.show` into a
string loop; JS and C print the same float with a different last digit.

Root cause, confirmed with a direct probe: both lanes search the shortest
precision that round-trips, C in `f32_text` (`comp.ts:443`, `snprintf
"%.*e"` then `strtof`), JS in `f32_show` (`x.toExponential(p - 1)` then
`Math.fround(Number(s))`). At an exact tie the libc rounds to even and
`toExponential` rounds up (ECMA-262: "if there are two such n, pick the
larger"):

```
135.953125  C: 1.3595312e+02   JS: 1.3595313e+2
0.15625     C: 1.5625e-01      JS: 1.5625e-1   (no tie at that precision)
```

Both strings round-trip to the same float, so `F32.read` agrees; only the
printed text differs. The interpreter shares the JS printer, so the C
lane is the odd one out.

Patch (C side, `f32_text`): after the shortest `p` is found, detect the
tie and round it up. Print the exact expansion once (`snprintf(tmp, 64,
"%.30e", (double)v)` is exact for every f32), and if the digits past
position `p` are a `5` followed only by zeros, re-print with `p` digits
from a value nudged up by one unit in the last place of the mantissa
string (increment the digit string with carry, keep the exponent). Ten
lines, no libm. Alternatively the JS side can round half to even by
checking the same tie on `x.toExponential(30)` and choosing the
`toExponential(p - 1)` of the neighbour below; the C patch is preferred
because the JS behaviour is the language's own and the interpreter uses
it too.

## The bracket wall: one expression of more than 85 binary ops (2 findings)

`17931146875850743826`, `17654569611860533016`: clang stops with `bracket
nesting level exceeded maximum of 256` on a line like

```
u32 r183_0 = U32_BIN(U32_BIN(U32_BIN( ... 97 deep ... , +, v177_0), +, v_1509), +, U32_BIN(v_1494, &, p5_76));
```

The CLI build fails the same way (`bend file -o out`), so it is the
emitter. This is class D of the earlier triages
(`repros/bracket_wall.bend`, `repros/c_bracket_wall_chain.bend`), whose
fix, a temporary every 64 levels, did not survive the emitter rewrite.

The pattern is a single source expression nesting more than 85 binary
operations, whatever binds it: the seal of a fuzzer program folds the
def's live variables into one value,

```
+r183 = ((((((p4 * p5 : U32) .^. p6 : U32) + p8 : U32) + p9 : U32) .^. p10 : U32) ... 97 ops
```

and `emit_intr` (`comp.ts:2146`) renders each operation by splicing its
operands' C text into the `U32_BIN($0, $o, $1)` template, so the
expression tree becomes one C expression. The macro expands to three
parenthesis levels per operation (`((u64)((u32)(a) o (u32)(b)))`), and
clang's limit is 256: 85 nested operations pass, 86 fail
(`repros/c_bracket_wall_expr.bend`, the smallest form: `def f(+a: U32,
+b: U32)` returning a chain of 86 `+`/`.^.`/`-`/`*` over `a` and `b`).
Let-bound or in tail position makes no difference now; both paths
render the same text. What does NOT trigger it: the same chain written
as 100 sequential lets (`v1 = (v0 + a)`, `v2 = (v1 .^. b)`, ...), since
every let, single-use or not, is emitted as its own `u32 vN_0 = ...;`
temporary. So only source code that nests 86 operators in one
expression is exposed: generated code, an unrolled hash or checksum, a
polynomial written inline.

Patch (`emit_intr`, `comp.ts:2146`), tried on a scratch copy of the
compiler: an intrinsic's operands are atoms. A compound operand (its
text holds a parenthesis) binds to a temporary through the existing
`emit_alias` before the operation, so an expression tree is emitted as
one statement per operation, exactly what the sequential-let form
already produces:

```
Term a_0 = U32_BIN(9ull, +, 1ull);
Term a_1 = U32_BIN(a_0, *, 2ull);
Term a_2 = U32_BIN(9ull, -, 3ull);
r0 = U32_BIN(a_1, ^, a_2);
```

The rule replaces the `dup` special case (`/\$(\d)[^]*\$\1/`, which
aliased an operand named twice by a template): a duplicated atom is
free and a duplicated compound is aliased by the new rule, so the regex
goes and the line becomes `ws.map((a) => /[()]/.test(a) ? emit_alias(fl,
a, "a") : a)`. Verified on a scratch copy of the compiler, the temporaries typed at the
operand's own kind (`u32` for a word, `Term` otherwise): the 86-op and a
300-op chain compile and run (clang crashes outright on the 300-op chain
even with `-fbracket-depth=4096`, and the Metal compiler has the same
256 limit with no option to raise it, so the flag is not an answer), the
100-let program is unchanged, and the 16 runtime benches print the same
output with no nested `U32_BIN` left. Measured over the 16 benches
(minimum of 5 runs, `--gpu off`):

| | current | atom operands |
|---|---|---|
| emission (bun, all 16) | 12.8 s | 13.1 s |
| clang -O3 (all 16) | 2.8 s | 2.8 s |
| C lines | 3,504-4,724 | +0.1% to +9.5% (nbody) |
| run, `--threads 1`, all 16 | 63.97 s | 63.18 s |
| run, `--threads 8`, all 16 | 11.64 s | 11.51 s |

Thirteen benches are identical to the millisecond in both lanes; three
float-heavy ones get faster with the flat form (`--threads 1`: nbody
5.80 s to 5.22 s, merkle 4.60 s to 4.52 s, mandelbrot 4.91 s to 4.84
s), since the nested `f32_rewrap(f32_unbox(..))` chains were the deepest
expressions and clang optimises the flat sequence better. None gets
slower. The Metal lane (four benches rebuilt with `-DBEND_METAL`, `--gpu
on`, minimum of 7): nbody, mandelbrot, bitonic and kmeans within run
noise of each other.

## An arity over 255 (1 finding, then the `arity-wall` skip)

`6224080003811562953` (also `findings/skipped/`, `reason=arity-wall`): the
emitter dies in `compile_tables` (`comp.ts:2704`) because `FID_ARITY_T` is
a `CONSTV u8` table and one segment has more than 255 parameters. The
program holds a list literal of ~550 `Map.set(..)` results (2,766 commas
on one line): every element is a call whose result is a live word until
the list node is built, so the segment resuming after the last call
carries every earlier result, and its parameter count is the literal's
length.

Patch, either side. Compiler: widen the arity tables (`CONSTV u16
FID_ARITY_T`, `fid_arity` already casts to `u32`; `CID_ARITY_T` may stay
`u8` since a constructor's field count is bounded by the parser) and the
`if (vals.some((v) => v > 255))` guard becomes `> 65535`; the segment's
frame words are indexed by `u32` already. Generator: `gen_list_lit` caps a
literal of call-valued elements at 64 (`fuzz.ts`, the list literal
production), which is what the fuzzer did for the skip class; the
compiler side is the real fix since base's own programs may hit it.

## Metal: a `!` loop next to a forking `!` def computes `%` wrong (1 finding)

`15433551208709355953`, `batch-only`: the eight-member program printed
`4294965866` on the Metal lane where C-SEQ prints `4294965996`, and no
member fails alone. The CLI build reproduces it deterministically (`bend
mb.bend -o mb; ./mb --gpu on` vs `--gpu off`), so it is not a harness
artifact.

Reduction: members 0 and 3 together are enough; only member 0's `rs16`
being live matters, and `rs16` holds `bt1!(3n, ..)`, a forking def (`a b
= bt1(q, ..) bt1(q, ..)`); member 3's diverging value is `xt3000013 =
tl3000015!(U32.to_nat(2065), U32.from_nat(3n)) * 130` with

```
def tl(+n: Nat, +a0: U32) -> U32:
  match n:
    case 0n:      (a0 - 10 : U32)
    case 1n+p:    tl(p, (4294967295 % a0 : U32))
```

`repros/comp_metal_two_bangs.bend` is the 30-line form: `rs()` runs `bt1!`,
`xt()` runs `tl!`; alone, `tl!` is right on the GPU; with `bt1!` in the
program it is wrong whichever runs first, and the emitted C for `tl` is
byte-identical in both builds (only the tables differ: `BANGS 2`, the
forking def's segments in `WL_TABLE`). Probing the loop at several counts
shows the first step itself is wrong: on the device `4294967295 % 3`
yields `2147483525`, `% 5` is right, and every later step chains from the
bad value (`n=2` gives `245`, `n=3` `185`).

`repros/comp_metal_two_bangs_probe.bend` runs the loop at several
counts and seeds next to the forking def (sequential vs `--gpu on`):

```
tl!(1, 3)     4294967286  2147483515    first step: 0xFFFFFFFF % 3 = 2147483525 on the device
tl!(2, 3)     4294967285  235           = (0xFFFFFFFF % 2147483525) - 10, exact from the bad value on
tl!(3, 3)     4294967286  175
tl!(10, 3)    4294967285  4294967286    the chain re-enters the 0 / 0xFFFFFFFF alternation, parity flipped
tl!(2065, 3)  4294967286  4294967285
tl!(n, 5)     equal                     0xFFFFFFFF % 5 is right
```

What triggers it, from twelve controlled builds (each a CLI build, run
`--gpu off` against `--gpu on`):

- **The dividend must be a compile-time constant.** The same remainder
  with the dividend as a parameter (`def md(n, x, a0)` looping `x % a0`,
  called as `md!(1n, 4294967295, 3)`) is right on the device in the same
  kernel.
- **The constant must round to 2^32 as a float**, i.e. lie within 128 of
  2^32: `4294967295`, `4294967294`, `4294967293`, `4294967291` and
  `4294967195` all fail for some divisors; `4294966295` (which rounds to
  4294966272), `3000000000` and `2147483649` are right for every divisor
  tried. The failing results are the true value plus or minus 2^31 and a
  small offset (`0xFFFFFFFF % 3` gives `a - 0x8000007A`; `0xFFFFFFFF / 3`
  gives `q + 0x80000029`), the signature of a division lowered through a
  float reciprocal whose fix-up steps cannot recover once the converted
  dividend is 2^32 rather than 2^32-1.
- **Only some divisors**: with `0xFFFFFFFF`, of the divisors 1-13, 15,
  17, 100, 255-257, 1000, 65535, 65536, 2^31 and 2^32-1 only `3` fails;
  with `4294967291` the divisors 3, 6, 9 and 11 fail and 13 is right;
  with `4294967195` 3, 6, 9, 11 and 13 all fail. The quotient
  `4294967295 / a0` fails for 3 too
  (`repros/comp_metal_two_bangs_dividends.bend`).
- **Only in some kernels, in Bend's emitted C.** The loop alone is right.
  It is wrong next to the forking def `bt1` (`a b = bt1(q, i*2) bt1(q,
  i*2+1); a ^ b`) with or without the multiply in its leaf, and right
  next to a forking def with trivial arguments or a non-forking `!`
  loop. The standalone kernel below shows what the other def changes:
  the form the backend sees the loop in.
- **Standalone, one expression, one file** (`repros/metal_urem_const/
  repro.m`, 28 lines: the expression `4294967295u % d` as a macro, run on
  the CPU with `d = argc + 2` and in an embedded kernel with `d = id + 3`
  on one thread, so the divisor is 3 at run time and unknown at compile
  time). The CPU prints `0`, the GPU `2147483525`;
  the quotient `4294967295u / (id + 3)` gives `3579139454` for
  `1431655765`. No loop, no guard, no second function. The same window
  and pattern hold: `4294966295u % (id + 3)` is right, `(4294967294u +
  id) % (id + 3)` (a runtime dividend) is right, `4294967195u % (id +
  7)` is wrong, and a divisor read from a buffer behaves like `id + 3`.
  Some loop forms around the expression hide it (a 32-bit counter, an
  up-counting 64-bit one) and Bend's form, a 64-bit counter decremented
  to zero in `for (;;)`, exposes it, which is the "some kernels" effect
  above: the backend has more than one lowering for a constant
  dividend and the surrounding code decides which one it takes.
- **Not the front end.** `xcrun metal -S -emit-llvm` of the passing and
  failing programs gives the same IR for the loop, `urem i32 -1, %phi`
  under the same zero guard, and the standalone kernel needs no
  guard at all; the fault is in Apple's AIR-to-GPU backend.
  `MTLLibraryOptimizationLevelSize` changes nothing; `MTLMathModeSafe`
  is already set (integer lowering is outside the math mode). Hand edits
  of the emitted C settle the workaround: typing the constant `u32`
  instead of `Term` or writing the zero guard as an `if` change nothing;
  a `volatile` dividend (`volatile u32 a_v = 4294967295u;`) makes the
  device correct, because the backend then takes its runtime path.

In the fuzzer's programs the shape is common: the generator likes the
literal `4294967295`, and `x % a0` with a loop-carried divisor is any
`tl` loop. In user programs it is a `U32.max % n` or a hash constant
near 2^32 divided by a variable inside a `!` def, so it is rare but
silent when it happens. This is the run's one true Metal miscompile and
the reason the batch harness saw it only with two members together.

Patch (emitter, device build only): take the division away from the
backend altogether. Under `#if DEVICE`, `u32_div`/`u32_mod`
(`OPERATIONS`, `comp.ts:174`) emit `u32_quo($0, $1)` / `u32_rem($0, $1)`,
helpers written in integer arithmetic only, so no division instruction
reaches the Metal compiler and no lowering choice can be wrong:

- the plain form, verified on the reduced program (`mb_ld`: device
  output correct): binary long division normalised by `clz`, `s = clz(b)
  - clz(a)` steps of compare-subtract-shift; 3 ops per step, at most 32
  steps, no float anywhere;
- the fast form, the one to ship after a proof and an exhaustive CPU
  check over every divisor: the divisor's reciprocal in 0.32 fixed
  point, one float `rcp` of the DIVISOR only as the seed (the dividend is
  never converted), one or two Newton steps with `mulhi`, then `q =
  mulhi(a, m)`, `r = a - q*b`, and a single compare-subtract fix-up; about
  ten integer ops, the same cost as the backend's own sequence.

The host build keeps the native `/` and `%`; the CUDA lane can share the
helper for uniformity. Two things that do not work, both tried on the
reduced program: a `noinline` helper (`__attribute__((noinline))` at file
scope, device output still wrong: the constant is propagated into it or
the attribute is ignored), and a `volatile` copy of the dividend (device
output correct, but it forces a memory round trip per division and
asserts nothing true about the value, so it is a stopgap at best). File
the kernel with Apple as well (`repros/comp_metal_two_bangs.bend`, `bend
file -o x; ./x --gpu-build` writes the Metal source).

## `memory fault` and zeroed show output on tiny pure mains (23 findings, not reproduced)

Sixteen `bend: memory fault (machine stack overflow?)` exits and seven
wrong show outputs, all C-SEQ, all on tiny pure `main() -> D0` programs
printed as literals, in every configuration (pure, threads, metal, io):

```
expected "D0a{9n}"                got "D0a{}"
expected "D0c{97}"                got "D0a{}"
expected "Some{D0a{}}"            got "Some{None{}}"
expected "((470, 'A'), D0a{})"    got "((470, 'A'), )"
```

The wrong outputs are what `show_val` prints when the words it reads are
zero: constructor 0 of the type, arity 0, an empty component. The signal
text is the runtime's SIGSEGV/SIGBUS handler.

What was tried:
- Every one of the 23 rebuilt with the CLI (`-O3`) and with the fuzzer's
  own flags (`clang -O1 -std=c11 -w -fno-slp-vectorize`) passes.
- Two of the rebuilt binaries ran 20,000 times each, 8 at a time, with
  `--threads 1 --gpu off`: 0 failures. 60 runs under 12 CPU hogs and 40
  under a memory hog: 0 failures.
- Chunk 15 replayed from its seed with the same compiler snapshot and
  config (`--threads 4 --io-pct 50 --keep`), 23,153 seeds: its two
  original failures (`12149412578496596517`, `15167771151944014068`) pass;
  the only failure is the deterministic generator reject below.
- The failing programs are not special: the same shapes pass by the tens
  of thousands.

Evidence for the cause: the timeline. Every failure of this class sits in
a burst of worker timeouts and out-of-memory RangeErrors (next sections):
01:05-01:40, 03:41-03:55, 05:51-05:58, 07:50-07:51, 23:12-23:28 UTC. The
run kept 10 Bun workers (each holding a checked base book plus its
programs), up to 8 clang processes and 8 running binaries (each reserving
a 2^43-byte `MAP_NORESERVE` pool plus 2 GB stacks) on 16 GB with 2 GB of
swap. The failures are load-correlated, not program-correlated.

Hypothesis (the strongest one, not proven): under exhausted memory the
kernel fails to back a touched page of the pool or the alternate signal
stack, the touch raises SIGBUS, the handler prints `memory fault`; the
seven "zero" outputs are the same episode landing between the
evaluator's writes and `show_val`'s reads on a page the kernel gave back
fresh. A second candidate, not excluded, is the file-backed pages of a
just-linked binary being re-read under pressure.

Patches:
- Runtime (`pool_stack`'s handler `err_trap`, `comp.ts` C template): use
  `SA_SIGINFO`, and when `si_addr` lies inside the pool or a stack
  reservation, print `out of memory at <offset> in the pool` instead of
  `memory fault (machine stack overflow?)`; the next run tells the classes
  apart by text. Also check `mprotect`/`sigaltstack` results (already
  done) and `sysconf`-derived limits at start.
- Harness (`fuzz.ts`, the C-SEQ leg): when a C-SEQ run of a program with
  fewer than N lines fails with a signal or an output mismatch, rerun the
  same binary up to three times before declaring a finding, and stamp
  the finding header with `vm_stat`'s free/compressed pages, `sysctl
  vm.swapusage` and the 1-minute load average; keep the group's build dir
  on failure without `--keep`.
- Driver: `--jobs 4 --pool 4` on a 16 GB machine; the pure and `--metal`
  chunks ran at 2-3 programs/s with 8 jobs because clang, not the fuzzer,
  was the bottleneck, so fewer jobs cost little.

## Generator rejects (4 findings, deterministic)

- `13170563434856890510`, `5974262862091448628`, `9395614603617028560`:
  `duplicate declaration: F32`. Families are named `"F" + uid`
  (`fuzz.ts:1563` and `:1640`); a uid of 32 mints `F32`, base's float
  type. Patch: name families `Fm<uid>` (and `Fn`/`Fv` are already taken
  by the Word idiom's minted names, keep those), or reserve every base
  name in `c.uid()`'s name check.
- `17444570799476821339`: `expected: a decreasing self-call, observed:
  mf3000036`. The family builder `def mf(n: I) -> F(n)` synthesizes each
  arm's value with `syn` (`mk_fam`, `fuzz.ts:1655`); inside the `0n` arm
  the goal was met through a registered def with a dependent parameter
  `F3000003(1n)`, and `syn` of that argument at a closed index chose the
  builder itself (`mf3000036(1n)`, the `mk_fam(c, goal.f)` production at
  `fuzz.ts:2483`), a self-call at a literal that does not shrink. The
  replay reproduces it at the same seed. Patch: while `mk_fam` generates
  a family's rows, put `"mk:fam:" + f.name` in `c.wip`, and in `syn`'s
  `T.app` case skip the builder production when the key is in `c.wip`
  (unfold the closed index to its arm instead, as the other production
  already does); the same guard `rd_ensure` uses for readers
  (`fuzz.ts:1954`).

## Skips

### `emit-c-stack-overflow` (13): out-of-memory RangeErrors

All 13 programs are 13-55 lines, most a `mk(U32.to_nat(<literal
expression>), ..)` over a small datatype. Each compiles with the CLI and
in a fresh fuzzer worker (`bun fuzz.ts 1 --seed 10595016358824126454`:
ok), and their positions inside their chunks range from 40 s to 29 min,
so they are not a worker-history effect either. The worker classifies
any `RangeError` from `compile_book` as a stack overflow
(`fuzz.ts:4243`, `:4286`, `:4307`), but JavaScriptCore raises
`RangeError: Out of memory` when the heap cannot grow (verified: `bun -e`
concatenating a 4 GB string prints `RangeError "Out of memory"`). The
timestamps fall in the same overload bursts as the memory faults.

Patch (harness): branch on the message, `/call stack/i` stays
`-stack-overflow`, `/out of memory/i` becomes `-oom` and is retried once
in a fresh worker before it is recorded; write the message into the skip
header either way.

### worker-timeout (27) and raw-worker-timeout (26)

The interpreter leg (`term_snf` over each def) has a 45 s budget
(`WORKER_TIMEOUT`). Three of the skipped seeds profiled on the idle
machine (`--profile --check-only`): 3.7 s, 2.7 s and 12.5 s, all in
`worker:sealed`/`worker:raw`, i.e. the JS interpreter on programs with
string appends, `match` on strings, Nat loops and families; under 8 jobs,
clang and GPU builds they cross 45 s. No leg disagrees on them. Patch:
scale the budget by the pool's observed slowdown (the ratio of a fixed
calibration program's interp time now versus at start), or split the
budget per def and record which def timed out so a real interpreter
cliff (`Nat.read`-like) shows as a repeated def name.

### The nine SIGTERM findings, deleted

`raw-crash`/`interp-crash` "worker died sig=SIGTERM": all at 09:44:24 and
09:53:38 local, the driver's between-chunk `pkill -f "fuzz.ts --worker"`
and my replay's own `timeout` hitting the replay's workers. Patch (driver
script): kill only the chunk's process group (`setsid` the chunk, `kill
-- -$pgid`), never by pattern.

## The compiler fix under test (uncommitted)

In `emit_body`, a def with a single call site is fused into its caller
(`emit_fuse`) instead of jumping to its own segment. A def whose return
type names a parameter (`def mf(n: I) -> F(n)`) has arms that return at
different layouts, and only its own segment, whose return is a box,
receives them all; fused into a caller typed at one index, the other
arms cannot convert and the emitter dies (`a layout mismatch`, `a
constructor outside its layout`). The fix is one condition on the
existing `once` test: a def whose return layout is a box (`lay_box(ret)`)
does not fuse into a segment whose return is not, so it jumps and its
return converts through the cut below. Four added lines, `ret` hoisted;
no new state. The four family-arm-layout repros build and match JS; the
16 runtime benches emit byte-identical C; over the 1,190 runnable tests
one program's C changes (`tests/check/dependent_function_arg.bend`,
`apply(P, f, n) -> P(n)` now jumps rather than fusing into main) and
prints the same. This run adds 265,735 programs with families, indexed
datatypes, propositions and dependent pairs on top of the earlier form
of the fix, and no layout finding.
